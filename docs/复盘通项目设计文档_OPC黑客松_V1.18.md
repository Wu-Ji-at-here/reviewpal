# 复盘通（ReviewPal）项目设计文档

黑客松 OPC（一人公司 / One Person Company）赛道

版本：V1.18（修订版 · 目标复盘打卡工具）　|　日期：2026 年 10 月 16 日

> 一句话：**把「每日进步五问」变成打卡卡片的工具** —— 五问填完，它告诉你今天推进到什么程度、明天第一步做什么。

---

## 一、项目概述

### 1.1 项目名称与定位

项目名称：复盘通（ReviewPal）

赛道定位：黑客松 OPC（One Person Company / 一人公司）赛道

一句话定位：**把"每日进步五问"变成一张打卡卡片的工具**——五问填完，它告诉你今天到底推进了什么、明天第一步做什么。

**产品性质**：本产品是**目标管理与复盘打卡工具**，只处理目标、计划、行动与推进度，不涉及医疗、心理评估或情绪疏导服务。（卡片模板最底部有一句可更换的短句位 `quote`，内置 100 句、随机轮换。）

核心方法：**目标 → 计划 → 实际 → 保持/优化 → 明日计划** 的五问闭环 + 推进度可视化。
### 1.2 问题洞察

- **目标与行动脱节**：大家会立目标、会做计划，但很少有人在一天结束时回头问一句"我今天做的事，到底有没有帮到目标"。
- **复盘流于形式**：现有工具要么只记流水账（记录完就完了），要么要求填写复杂的结构模板，坚持三天就放弃。
- **计划与实际的差距看不见**：没有"计划 vs 实际"的对照，也没有跨天的趋势，走偏了自己也不知道。
### 1.3 解决方案

- **五问引导输入**：把"复盘"拆成每日进步五问（目标 / 计划 / 实际 / 保持与优化 / 明日计划），分 5 个小模块分步引导，降低填写门槛。
- **推进度判定**：根据第 3 问的自评与填写内容，判定今天属于「超额达成 / 按计划达成 / 部分完成 / 偏离目标 / 未推进」五档之一，并换算成 0-100 分。
- **可视化闭环**：推进度同时驱动界面配色、卡片顶条与月热力图——**这周有没有走偏，一眼看得出来**。
- **可沉淀的成果卡**：生成的每日复盘卡可导出 PNG；保存后自动进入下方「我的打卡墙」（本地私有，不对外公开）。
### 1.4 核心产出物

- **即时产出**：一张「每日复盘卡」，按五问结构排版（目标 / 计划 / 实际 / 保持与优化 / 明日计划 + 推进度），底部一句可更换的鸡汤（内置 100 句、随机轮换）；可导出 PNG，保存后自动进入「我的打卡墙」。
- **长期产出**：结构化复盘库（SQLite），支持按日期查回、关键词检索、月热力图与推进度趋势；周期性报告属 P2 愿景，见 8.3。
## 二、核心功能模块设计

### 2.1 每日五问（核心输入结构 · 界面区块「每日五问」）

**场景**：用户每天花 2-3 分钟，回答"每日进步五问"，完成当日打卡。

**五问结构（唯一输入定义）**

| # | 问题 | 引导说明 | 输入方式 |
|---|---|---|---|
| 1 | 我的目标是？ | 分长期目标与短期目标两栏 | 两个单行输入框 |
| 2 | 我今天原本的计划是什么？ | 写你今天打算做什么 | 多行输入 |
| 3 | 我今天实际做了什么？**今天的行为，是否有助于目标的实现？** | 写实际发生的；再选一个自评：**有助于 / 部分有助于 / 无助于** | 多行输入 + 三选一 |
| 4 | 从今天来看，哪些做得比较好、可以保持？哪些做得不够好、需要改正优化？ | 分"保持"与"优化"两栏 | 两个单行输入框 |
| 5 | 明天的任务和计划 | 写明天第一件要做的事 | 多行输入 |

**交互设计：分步引导，不做"大空箱子"**

- 默认**一步一问**：一次只显示 1 个模块，顶部有 1-5 的进度点（可点击跳转），下方是「上一步 / 下一步」。
- 每个模块带**引导性占位文案**（例："长期：例如「年内独立完成一个我自己满意的产品」"），让第一次使用的人也知道该写什么颗粒度。
- 第 3 问的"是否有助于目标"是**用户自己选**的，不由系统猜测——这是推进度判定的主要依据。


### 2.2 三明治协同复盘流（核心交互）

这是"复盘通"的人机协同核心架构，将 AI 深度嵌入复盘工作流：

- **顶层（人类主导）**：用户提供原始数据（五问作答：目标 / 计划 / 实际 / 保持与优化 / 明日计划），设定复盘意图与边界。
- **中层（AI 主导）**：执行语义分析与结构化整理，运行"计划 vs 实际对照"与"提炼保持 / 优化"逻辑，输出符合统一契约的结构化 JSON（见附件 F）。
- **底层（人类主导）**：前端渲染 AI 整理的结论，用户对每一条二次修改、确认或润色——界面上就是「确认与修改」区块；点一次「确认并保存」即写入复盘库。

技术体现：用户修正的数据（`edit_history`）反传给 AI 作为下一轮对话上下文，完整展示 "Human in the Loop" 的协同深度。

### 2.3 每日复盘卡（Daily Review Card）

功能：把当日五问与推进度渲染成一张可导出的卡片。

**卡片结构（按五问排版）**

| 区块 | 内容来源 |
|---|---|
| ① 我的目标 | 第 1 问（长期 + 短期） |
| ② 原本的计划 | 第 2 问 |
| ③ 实际做了什么 | 第 3 问 + 自评"是否有助于目标" |
| ④ 保持 / 优化 | 第 4 问（AI 提炼后可编辑） |
| ⑤ 明天的计划 | 第 5 问 / AI 生成的 `tomorrow_focus` |
| 推进度 | `progress.label` + `progress.score`，配进度条 |
| **今日一句（鸡汤位）** | `quote` —— **内置 100 句、随机轮换**（卡片末尾展示） |

**导出**：用 Canvas 原生出图（不引入 html2canvas），导出 720×1240 的 PNG。

**主题**：暖色极简 / 赛博朋克 **两套**主题，卡片自动跟随当前主题与推进度配色。

**分享方向**：不做二维码与朋友圈裂变，也不做公开分享；回顾只沉淀在本地「我的打卡墙」（见 2.5）。
### 2.4 长周期沉淀与月热力图

两条长期能力，都在"我的记录墙"里（不单独占比重）：

- **月热力图**：本月每天一个格子，颜色从**无色渐变到红色**表示当天推进度高低（灰格＝未记录）。一眼看出"这个月哪几天在推进、哪几天停了"。
- **记录墙（搜索 / 回看）**：列出全部记录，可按**推进度**筛选、按关键词搜索、点击任意一条**回看并继续编辑**；卡片可「删除」。

> 说明：V1.7 之后取消"情绪/心理"维度，长期视图只反映**任务推进情况**。
### 2.5 我的记录墙与打卡墙

**定位**：网站最下面的**个人成果区**（本地私有、不对外公开），把你的复盘卡排列出来，形成"我坚持了多久"的可视证据。

**规则**

- 保存即入墙：记录**保存后自动出现在打卡墙**，无需任何"公开/同意"操作（不做社区，也不对外公开）。
- **只展示本人的卡片**：接口按归属过滤（`GET /api/wall?mine=<访客ID>`），**别人的卡片不会出现在你的墙上，你也不会出现在别人的墙上**。
- 卡片显示：日期、今日总结、明日计划、推进度；卡片可「删除」。
- 打卡墙提供**按推进度**的筛选：**全部 / 超额达成 / 按计划达成 / 部分完成 / 偏离目标 / 未推进**（带颜色点）；另有**关键词搜索**。卡片操作按钮为「删除」。
- 可**删除**：任意卡片可删除，删除后从本地库移除、不可恢复（对应 §10.1「可删除」）。
- 演示用：「填充我的示例数据」可一次灌入 10 张带「示例」标记的卡片（归属为当前访客，可一键清空）。

**本期边界：不做跨用户互看**

比赛阶段的目标是**把项目演示清楚**，而不是运营一个社区。跨用户互看 / 点赞 / 评论会立刻带来三件必须配套的事——**账号体系、内容审核、举报处置**，任何一件没做好都可能变成现场被追问的漏洞。因此：

- 本期：打卡墙**只展示本人卡片**；点赞、评论、举报等跨用户功能**不实现、不演示**；
- 发展前景：完整社区方案移入 **§8.3 愿景清单**，在被评委问到时口头说明。
## 三、AI 交互与 Prompt 设计规范

### 3.1 AI 人设设定

一句话：**清晰、务实、不说空话的"复盘教练"**——把五问整理成"明天能照着做"的结论；不评判人格、不喊口号、不涉及医疗与心理服务。

> 完整人设与规则的可执行定义见**附件 A**（与后端 `server/prompts/system-v1.md` 同源），本节不重复。
### 3.2 核心 Prompt 机制

三大机制（全部围绕**目标复盘**）：

- **对照机制**：强制对照"计划 vs 实际 vs 目标"，先指出差距出在哪，再给结论。
- **提炼机制**：从用户自己的话里提炼 `keep`（可复制的做法）与 `improve`（可改的动作），**不许输出形容词**（"更努力""更专注"一律不接受）。
- **落地机制**：`tomorrow_focus` 必须"具体 + 数字 + 30 分钟内能开工"（例："明天 9:00-10:30 手机静音，只写第三章"）。

输出字段与取值以 **附件 F（唯一真相源）** 为准；不涉及任何心理/情绪字段。
### 3.3 输出格式规范

AI 必须严格返回 JSON，字段以 **附件 F《统一数据契约 v2》** 为唯一真相源（对应文件 `review-record.schema.json`）。字段来源映射见 11.1。**任何 Prompt 的输出字段若不在契约中，一律视为缺陷，需要么补进契约、要么删除。**

## 四、数据结构设计

每次复盘的核心数据单元为结构化 JSON：前端据此渲染卡片与月热力图，后端据此沉淀复盘库。

**字段定义、取值约束、枚举范围的唯一定义处为附件 F《统一数据契约 v3》（`review-record.schema.json`）**，正文不再重复罗列。

字段分六组：

| 分组 | 字段 | 说明 |
|---|---|---|
| 标识 | `id`、`date`、`created_at` | 由后端入库时生成 |
| 五问原始作答 | `answers.{goal_long, goal_short, plan, actual, alignment, keep, improve, tomorrow}` | 用户输入，原样保存用于回溯 |
| AI 整理结果 | `summary`、`key_insight`、`keep`、`improve`、`tomorrow_focus`、`tags` | 卡片主要渲染来源 |
| 推进度 | `progress.{status, label, score, reason}` | 5 档 + 0-100 分，驱动配色与月热力图 |
| 展示 | `public`、`published_at` | **保留字段（本期不使用）**；不对外公开 |
| 模板预留 | `quote` | 鸡汤位：**内置 100 句、随机轮换（也可手动挑一句固定）、随卡片入库** |
| 元数据 | `user_edited`、`edit_history` | 用户二次修改记录，反哺下一轮 |

## 五、技术架构与 Pi Agent 协同方案

### 5.1 技术栈选型

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | React + Vite + Tailwind CSS | 技术栈定一端，不做双端待定 |
| 后端（新增） | Node.js + Express（单文件即可） | 拼装 Prompt、调用模型、写入数据库、限流 |
| 模型运行时 | Pi Agent（MIT 开源协议，极简 Agent Harness 架构） | 与"后端直接调用模型 API"二选一；定版后不再更改，避免两套调用逻辑并存 |
| 大模型 | DeepSeek 现行旗舰 / 轻量文本模型 | 通过 provider 配置或官方集成接入；**模型 id 以调用当日官方模型列表为准** |
| 数据库 | SQLite（`better-sqlite3`） | 服务端单文件库，零配置，适合黑客松周期 |
| 图片生成 | html2canvas / Canvas API | 将 DOM 渲染为分享图片 |
| 数据校验 | zod / ajv | 入库前校验模型输出是否符合契约 |

**关于模型配置的重要说明**：

- `deepseek-v3` 这类写法在现行的 DeepSeek API 中**已不可用**；历史上常用的 `deepseek-chat` / `deepseek-reasoner` 亦已停止服务。当前应使用官方文档中列出的现行文本模型 id。
- 请勿把模型名硬编码进代码：统一放在 `.env`（如 `MODEL_ID=`）或 Pi Agent 的 provider 配置中，**换模型只改一处**。
- 演示请选用响应快、单价低的轻量模型；推理型模型首字延迟大，不适合现场演示。
- DeepSeek 存在峰谷计费（工作日白天高峰时段单价更高）。**路演多在工作日白天，成本按高峰期估算。**
- **动手前先做一次最小连通性验证**：用 Pi Agent 的官方登录方式，或用 `curl` 直连一次，确认 Key 与模型 id 均可用。

### 5.2 Pi Agent 架构优势

选择 Pi Agent 的核心理由：

- MIT 开源许可，个人项目可直接使用，无知识产权风险。
- 极简 Agent Harness：模型大脑、Agent Loop、工具调用、上下文管理、用户确认层清晰分离。
- 支持多模型切换（OpenAI / DeepSeek / Anthropic / Ollama 本地模型等），不绑定单一厂商。

> 使用建议：优先使用 Pi Agent 的官方 provider 登录方式完成鉴权，而不是手工维护配置文件——手工配置出错时排查成本很高。系统提示词（附件 A）可作为项目级 System Prompt 注入，便于版本管理。

### 5.3 人机协同可视化

在生成结果出现前，用三个标签依次点亮，可视化 AI 的整理过程（**3 步，约 1 秒**，既够看又不拖节奏）：

- [读取五问作答] → [比对计划与实际] → [生成建议与推进度]

目的：向评委直观展示"我在指挥 AI 按结构整理"，而非"喂一段话等答案"。该组件同时承担"模型调用等待期"的视觉占位，把延迟变成展示点。

**界面分组（页面布局约定）**：主区是**一条横向滚动带**，里面**并排 4 个分组**——**左右滚动即换组**（底部有常驻滚动条，可点可拖；也可直接按住卡片左右拖拽）；**组内卡片上下排列**；记录墙与数据说明常驻在下方——

| 屏 | 内容 | 理由 |
|---|---|---|
| 第 1 组 | 每日五问（上）+ 推进度判定（下） | 输入与判定是一条连续动线，绑成一组上下排列 |
| 第 2 组 | 确认与修改 | 人在回路，独立成组便于逐条校对 |
| 第 3 组 | 每日复盘卡 | 产出物，独立成组方便截图 / 导出 |
| 第 4 组 | 坚持打卡（月热力图） | 长期视图，独立成组 |
| 下方常驻 | 我的记录墙 + 数据说明（页脚） | 需要随时可查，不放进横向卡片带里 |


### 5.4 密钥安全与最小后端代理

**问题**：若由前端直接调用大模型 API，API Key 会随构建产物暴露给任何访问者，可被刷爆额度；浏览器直连还存在跨域限制。

**方案**：新增一个最小后端代理，所有模型调用经由服务端发起。

```
浏览器  --(用户输入，不含密钥)-->  后端 /api/review
后端    --(服务端 Key + System Prompt)-->  大模型
大模型  --(结构化 JSON)-->  后端  --(校验后的 JSON)-->  浏览器渲染卡片
```

要求：

- API Key 只存放于服务端 `.env`，**不得出现在任何前端代码、构建产物或浏览器请求中**。
- 服务端对模型输出做契约校验（附件 F），校验失败则重试一次，仍失败则走兜底模板。
- 服务端做基础限流（如单 IP 每分钟 N 次），并在模型控制台设置消费上限。
- 此设计本身即为路演加分项：可明确声明"密钥不落前端"。

### 5.5 数据流一句话说明

> 用户输入 → 后端拼装 Prompt 并调用模型 → 模型返回结构化 JSON → 后端校验后写入 SQLite → 前端渲染复盘卡 → 用户确认后入库定稿。

该句用于路演统一口径，避免"数据到底上不上云"的前后不一致（详见 10.3）。

## 六、项目定位与路演规划（本期不考虑商用）

**定位声明**：本作品参加黑客松，**本期不考虑商业化**。不设付费版本、不做定价与转化设计，全部功能免费开放。

- **免费提供**：五问引导输入、推进度判定、每日复盘卡（导出 PNG）、月热力图、记录墙（检索与回看）、打卡墙。
- **明确不做**：付费墙、订阅制、按席位收费、To B 版本、支付通道等商业化设计——本期全部功能免费开放。

**路演重点**：不讲商业故事，把时间留给两件事——产品是否真的好用，以及"一个人如何用 AI 把它做出来"。

**成本说明**：唯一可控成本是模型调用费（高峰时段单价更高）。内测期以 Mock 模式为主、真实调用少量多次，控制成本。

**MVP 验证计划**：比赛期间找 3-5 名同学/同事真实使用一周，收集"是否愿意第二天继续填"与卡片可执行性反馈，作为路演证据。
## 七、风险识别与演示预案

| 风险 | 触发场景 | 应对方案 |
|---|---|---|
| 演示翻车 | 现场模型调用失败 / 超时 | **双轨机制**：真实调用与 Mock 一键切换（`MOCK` 环境变量）；并备有提前录制的完整跑通视频 |
| 网络不稳 | 现场 Wi-Fi 拥塞 | 手机热点备用；不把现场 Wi-Fi 作为唯一链路 |
| 延迟过高 | 模型首字慢 | 选轻量模型；等待期间展示"AI 正在按结构整理"的思考流 |
| 额度耗尽 | 现场调用量大 | 提前充值并设置消费上限；服务端限流 |
| 模型抽风 | 输出非 JSON 或缺字段 | 契约校验 + 重试一次 + 兜底模板（见 11） |
| **跑偏成"心理产品"** | 表述或功能里混入情绪 / 心理内容 | **明确边界**：全文与界面不出现心理相关功能；唯一保留的是卡片末尾一句**可更换的鸡汤**（内置 100 句、随机轮换） |

| 口径不一致 | 评委追问数据与技术细节 | 统一口径：数据流一句话（5.5）、P0 验收清单（8.1）、Key 不落前端（5.4） |

## 九、留存机制设计

复盘 / 日记类产品的真实死因是"三天新鲜感"。本章只回答一个问题：用户凭什么第二天还打开。

> **交付标注**：本章机制均为留存设计，属路线图，不占用 P0 八项与 P1 分组额度，也不进入现场演示承诺。

### 9.1 月热力图与连续天数

- **月热力图**（界面区块「坚持打卡」）：本月每天一格，颜色从**无色到红色**表示当天推进度分数（0 分/未记录＝无色，越高越红）。这是"坚持"最直观的证据，也是路演时最好看的一屏。
- **弱惩罚连续机制**：连续天数用火焰呈现（火苗 → 小火 → 火焰），**中断不清零、只降级**；今天还没记录不算断。
- 情绪低谷时的"轻打卡"改为**低门槛打卡**：第 3 问只写一句也算完成当天记录。
### 9.2 成长可视化回访钩子

- 卡片自带"昨天的你"对比：同指标（专注度 / 积极情绪）日环比，制造"想看看今天的进步"的回访动机。
- 记录回顾周报式推送（P2 愿景）：每周一推送上周 Top3 记录回顾，唤起打开。

### 9.3 不做分享裂变（本地沉淀）

**不做**二维码与朋友圈裂变，也不做任何公开分享；回顾只沉淀在本机的**我的打卡墙**。

理由：目标与复盘内容属于私人数据，公开的代价大于分享收益。规则见 §2.5，本节不重复。
## 十、数据与隐私专章

本产品处理的是**目标与工作复盘数据**，不属于心理或健康类敏感信息；相应地，本产品不提供危机干预或心理疏导类服务。

### 10.1 数据原则

- **最小必要**：只收集五问作答；调用模型时只发送本轮填写的文本，不上传历史全量库。
- **全本地私有**：数据只存在本机 SQLite，**不进入任何公开页面、不对外分享**。
- **本地优先**：数据存放于部署方本地 SQLite（`data/reviewpal.db`）；云同步为后续可选能力。
- **可删除**：用户可删除自己的记录（本期为本地库，删除即从文件移除）。

### 10.2 数据不公开（本期无发布机制）

三条原则（实现细节见 §2.5）：

1. **不公开**：本期没有任何"发布 / 公开"入口；打卡墙只在本机展示你自己的卡片；
2. **展示收敛**：即使在本机，卡片也只呈现日期、`summary`、`tomorrow_focus`、`progress` 等摘要；
3. **可删除**：任意记录可随时删除，删除即从本地库移除（见 §10.1「可删除」）。
### 10.3 数据策略自洽

内测期数据存于本地部署的服务端；产品默认本地优先、云同步可选加密。路演口径统一为这一句，不再出现"上不上云"的两头表述。

### 10.4 面向用户的说明文案（可直接使用）

**数据说明（常驻）**

> 复盘通会把你的五问作答保存在本机后端（`data/reviewpal.db`），默认**只有你自己能看到**。调用 AI 时只发送你本轮填写的内容。你可以在界面上删除自己的记录。

（本期无"发布同意"文案。）



**隐私提示**

> 数据只存本机、不对外公开；但本机若多人共用，请注意复盘内容里的私人信息。

### 10.5 用词红线

界面与文案中**不得出现**："治疗、干预、疗效、诊断、抑郁、焦虑、心理测评、情绪疗愈"等医疗或心理宣称；也不得用"心理""情绪陪伴"来描述本产品。唯一例外是卡片末尾那句**可更换的鸡汤**（内置 100 句、随机轮换）。
## 十一、数据字段对齐说明

唯一定义处为附件 F《统一数据契约 v3》（`review-record.schema.json`）。

### 11.1 字段来源

字段的**唯一定义处是附件 F**。一句话概括来源：`id` / `date` / `created_at` / `public` / `published_at` 由**后端生成**；`answers`、`user_edited`、`edit_history` 由**前端捕获**；其余内容字段由 **AI 输出**。正文与附件不重复列字段表。
### 11.2 判定规则与可空约定

- `progress.status` 只能取 `advance / on_track / partial / off_track / stalled`；`score` 为 0-100 整数，须与 status 一致。
- **判定优先级**：用户第 3 问的自评（`alignment`）优先；未选择时才用关键词兜底（停滞 / 偏离 / 部分完成 / 超额 / 完成）。
- `improve` 与 `tomorrow_focus` 允许为空数组 / 空字符串（信息不足时 AI 必须写"信息不足"，不得脑补）。
- `quote` 内置 100 句、随机轮换，随卡片入库。

## 十二、效果评测方案

"有温度、不无聊"不能只是口号，需可验证。本节给出主观、行为、质量三类评测指标。

### 12.1 主观评测

- 卡片可执行性打分（5 分制，目标 ≥ 4 分）："明天的第一件事"是否具体到能立刻开工。
- SUS 简化版易用性问卷，衡量结构化输入门槛是否足够低。

### 12.2 行为评测

次日留存率、7 日留存率、平均复盘字数趋势（验证留存与深度双假设）。

### 12.3 质量评测

抽取 AI 输出样本，标注两项指标：

- **可执行率**：`tomorrow_focus` 是否满足"具体 + 数字 + 30 分钟内可开工"。
- **空话率**：`keep` / `improve` 是否出现"更努力""保持专注""加油"这类不可执行表述（目标 ≤ 10%）。

执行方式：模型初判 + 人工抽检 10 条复核。

> 12.1 的主观评测聚焦两项：**卡片可执行性打分**与"是否愿意第二天继续填"（坚持意愿）。

## 十五、路演一页纸与评委 Q&A 弹药（上台用）

### 15.1 60 秒路演大纲（作战地图）

- **一句话定位**：把「每日进步五问」变成一张打卡卡片的工具。
- **开场钩子**：我们每天都在立目标，但很少有人能说清"今天做的这件事，到底有没有帮到目标"。
- **P0 真实跑通动线**：一屏五问 → 推进度判定 → 思考流 → 复盘卡 → 导出 PNG → 确认并保存 → 记录墙与月热力图。
- **差异化**：不是"记流水账"，而是**计划 vs 实际 vs 目标**的三方对照；推进度变成颜色和月热力图，一眼看出这周有没有走偏。
- **收尾**：它不生产漂亮话，只帮你把"今天到底推进了什么"说清楚。
- **可信度承诺**：现场真实调用模型，并备有保底录屏与 Mock 一键切换。

### 15.2 评委 Q&A 弹药库

**Q1 复盘工具为什么不做情绪支持、不给安慰？**
答：这是刻意的边界。我们做的是**目标与行动复盘**，不是心理产品。越界谈情绪，既不够专业，也有合规风险；所以我们把力气全放在"计划与实际的差距"上。

**Q2 五问会不会太重、坚持不下来？**
答：分步引导——默认一次只问一个模块，顶部进度点可跳转；每问都允许留空，只填第 3 问也能出结果。

**Q3 推进度怎么判定？会不会瞎判？**
答：**用户自评优先**——第 3 问里"今天的行为是否有助于目标"是你自己选的；本地关键词规则只在没选时兜底。界面上会直接显示判定依据 `reason`，不服可以改。

**Q4 数据隐私怎么保证？**
答：全本地私有：数据只存本机 SQLite；调用 AI 只发本轮文本；不提供任何"公开 / 分享"入口。

**Q5 你一个人做的，AI 帮你写了多少？（OPC 赛道必问）**
答：AI 负责实现，我负责定义。产品定位、五问结构、推进度规则、数据结构与边界由我决定；AI 加速了编码与措辞候选。开发日志与 Prompt 版本记录可直接查阅。

**Q6 为什么不去做商业化了？**
答：本期把目标收敛到"产品是否真的好用 + 一个人如何用 AI 做出来"。商业模式留到验证之后再谈，路演不占时间。

**Q7 打卡墙会不会变成垃圾场？**
答：不会——本期没有公开机制，打卡墙只在本机展示你自己的卡片，且可随时删除。

**Q8 为什么取消朋友圈分享？**
答：目标与复盘内容属于私人数据，公开的代价大于分享收益；回顾只沉淀在本机打卡墙。

## 附件 A：完整 System Prompt（目标复盘教练版）

以下为后端实际调用的系统提示词（与 `outputs/reviewpal/server/prompts/system-v1.md` 同源）：

```
# 复盘通 System Prompt · v3（目标复盘教练版）
对应文档：附件 A · §3.1 人设

【这是什么】发给大模型的系统提示词。V3 起，本产品**只做目标复盘与行动梳理**，
不做任何心理判断、情绪疏导、危机干预，也不涉及心理咨询相关表述。

---

【角色设定】
你是一位清晰、务实、不说空话的"复盘教练"。你的工作是把用户今天的目标、计划与实际对照，
整理成**可以明天照着做**的结论。你不评判用户的人格，也不谈感受，只谈事实与下一步。

【硬性边界（必须遵守）】
1. 不谈论情绪、心理状态、心理疾病；不做任何心理评估或疏导；遇到情绪类描述，只把它当作"今天发生的事"来记录，不展开。
2. 不评判人格（不说"你是个拖延的人"），只描述行为与结果。
3. 不说空话、不喊口号。所有结论必须能对应到具体动作。
4. 不编造用户没提供的事实。信息不足时，宁可写"信息不足"，也不要脑补。

【核心任务：把"五问"变成可执行的结论】
围绕这五个问题输出：
1. 我的目标是？（长期 / 短期）
2. 今天原本的计划是什么？
3. 今天实际做了什么？今天的行行为是否有助于目标的实现？
4. 哪些做得好、可以保持？哪些做得不够好、需要优化？
5. 明天的任务和计划

要求：
- `summary`：一句话说清"今天围绕哪个目标、实际推进到什么程度"（不超过 60 字）。
- `key_insight`：一条最重要的发现，必须解释"为什么"——计划与实际的差距出在哪。
- `keep`：从用户填写的内容里提炼 1-3 条**具体可复制的做法**（不是形容词）。
- `improve`：1-3 条**具体可改的动作**（不是"要更努力"这种空话）。
- `tomorrow_focus`：明天第一件事，要求"具体 + 数字 + 能在 30 分钟内开工"。
- `tags`：2-4 个场景标签（如 工作 / 学习 / 运动 / 写作 / 沟通）。
- `progress`：推进度对象 `{ status, label, score, reason }`。
  status 只能取：advance（超额达成）/ on_track（按计划达成）/ partial（部分完成）/ off_track（偏离目标）/ stalled（未推进）。
  score 为 0-100 的整数，必须与 status 一致（advance 约 90+ / on_track 约 75-85 / partial 约 50-65 / off_track 约 25-40 / stalled 约 10-20）。

【输出格式 · 严格 JSON】
必须输出合法 JSON，不要任何解释文字，不要使用 ``` 代码围栏：

## 附件 C：Agent 运行时环境搭建与模型接入指南

**步骤一：前置环境**

确保电脑安装 Node.js 22.19.0 或更高版本（推荐最新版长期支持版本）。

```
node --version
```

**步骤二：安装 Agent 运行时**

```
npm install -g --ignore-scripts @earendil-works/pi-coding-agent
```

验证安装（另可用官方安装脚本 `https://pi.dev/install.ps1` 一键安装）：

```
pi --version
```

> 说明：安装命令中的 `--ignore-scripts` 是官方推荐写法，正常安装不需要依赖生命周期脚本，不必担心。

**步骤三：获取模型 API Key**

前往模型厂商开放平台注册账号，在控制台创建 API Key 并保存。**Key 只放进服务端 `.env`。**

**步骤四：接入模型（推荐用官方登录，而非手工配置）**

优先使用运行时的官方登录 / 模型选择流程完成鉴权——手工维护配置文件容易出错、排查成本高。

如需手工配置 provider，可参考以下结构（**模型 id 必须填官方当前可用的值，示例中为占位写法，请以厂商当日文档为准**）：

```
{
  "providers": {
    "deepseek": {
      "baseUrl": "https://api.deepseek.com",
      "api": "openai-completions",
      "apiKey": "sk-xxxxxxxxxxxx",
      "models": [
        {
          "id": "<MODEL_ID_以官方文档为准>",
          "name": "DeepSeek 文本模型",
          "contextWindow": "<官方值>",
          "maxTokens": "<官方值>"
        }
      ]
    }
  }
}
```

配置文件位置（如无则手动新建）：

- macOS / Linux：`~/.pi/agent/models.json`
- Windows：`%USERPROFILE%\.pi\agent\models.json`

**步骤五：最小连通性验证（先做这一步）**

在终端进入项目文件夹启动运行时，选中模型后输入一句话测试，能正常回复即代表接入成功。进一步可用 `curl` 直连模型接口验证 Key 与模型 id：

```
curl https://api.deepseek.com/chat/completions -H "Content-Type: application/json" -H "Authorization: Bearer $DEEPSEEK_API_KEY" -d "{\"model\":\"<MODEL_ID>\",\"messages\":[{\"role\":\"user\",\"content\":\"你好\"}]}"
```

**步骤六：时效校验清单（上线 / 路演前各做一次）**

- 模型 id 是否为官方当前可用值；
- 单价与峰谷计费时段；
- 账户余额与消费上限是否已设置。

## 附件 D：前端核心 UI 组件代码

### D.1 动效规范

界面不包含呼吸引导、共情或转介类组件。保留的动效只有两处：**AI 思考流**（D.2）与**卡片主题过渡**（D.3）。

所有动效遵循 `prefers-reduced-motion`：系统开启"减少动态效果"时，动画一律降级为静态。节奏保持在低频（4 秒周期 ≈ 0.25Hz），不做闪烁。
### D.2 AI 思考过程可视化组件

在 AI 处理复盘数据期间，以标签流的形式展示思考步骤，让评委直观看到"AI 按框架思考"，同时充当等待动画：

```html
<div class="ai-thinking-flow">
  <div class="thinking-step active" data-step="1">
    <span class="step-tag">[读取五问作答]</span>
    <span class="step-progress"></span>
  </div>
  <div class="thinking-step" data-step="2">
    <span class="step-tag">[选择专家模块]</span>
  </div>
  <div class="thinking-step" data-step="3">
    <span class="step-tag">[提取成功片段]</span>
  </div>
  <div class="thinking-step" data-step="4">
    <span class="step-tag">[生成微建议]</span>
  </div>
</div>
```

```css

### D.3 复盘卡主题切换说明

卡片通过切换 CSS 变量实现一键变换（P0 只做极简风，其余为 P1-A）：

- 极简风（minimalist）：白底黑字，大量留白，sans-serif 字体。
- 赛博朋克风（cyberpunk）：暗底（#0a0a2e）+ 霓虹色文字（#00f5ff, #ff00e5），发光边框。
- 学术风（academic）：米白底 + 衬线字体 + 细线边框 + 脚注格式。

### D.4 居中轮播布局与 Apple HIG 视觉规范（V1.18）

**布局：一屏一组（幻灯片式）**

- 页面按「分组」组织：**第 1 组＝区块 1**（每日五问，左右两栏：当前问题+步骤 / 五问清单+操作）、**第 2 组＝区块 3**（确认与修改）、**第 3 组＝区块 4**（复盘卡，含推进度）、**第 4 组＝区块 5**（坚持打卡）；**打卡墙（区块 6）与数据说明常驻页面下方**。原「区块 2 推进度判定」面板**已移除**，推进度改在区块 4 的复盘卡上呈现并驱动配色。
- 各组**等高**；相邻组**不再缩放、仅变暗并露出**，保证顶边与当前组严格对齐。
- 当前组**居中**显示，左右两侧露出**相邻组**（缩到约 0.9 倍、可点击）；**点击任意侧边卡片即切到该组**，并配 **键盘 ← →** 与底部圆点（不再用拖拽/滑动），切换带平移动画。
- 每组**等高、一屏放得下**，不出现纵向滚动条。

**卡片瘦身（避免"大卡片"）**

- 区块 1（五问）：保持**一步一问**，一屏只有一个问题卡，整体高度可控。
- 区块 3（确认与修改）：6 个字段改为**两列网格**（`summary` 跨两列，其余两两并排），显著降低高度。
- 各组顶部对齐、等高，切换时版式稳定。

**Apple HIG 视觉规范**

- 字体：系统字体栈（`-apple-system / SF Pro / PingFang SC / Microsoft YaHei`），正文 15px、行高 1.5。
- 控件：分段控件（Segmented Control）用于主题与打卡墙筛选；按钮圆角 12px；可点区域 ≥ 44pt。
- 层级：分组卡片圆角 18px、1px 细边 + 柔和阴影；顶栏毛玻璃（backdrop-blur）。
- 深浅色：暖色极简（浅色）/ 赛博朋克（深色）；`prefers-reduced-motion` 时动效降级为静态。

**打卡墙筛选（V1.18）**

- 按**推进度**筛选：**全部 / 超额达成 / 按计划达成 / 部分完成 / 偏离目标 / 未推进**（带颜色点）。
- 另有**关键词搜索**；卡片动作为「**删除**」。
